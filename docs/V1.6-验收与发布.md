# V1.6 验收与发布

本文说明 V1.6 的预览、发布、回滚和本地数据兼容性。每次构建的提交号、发布包 SHA256 和测试结果，以本仓库 **Releases** 和 **Actions** 页面为准。

## 1. 仓库与网址

| | 地址 | 内容 |
|---|---|---|
| 源码仓库（公开） | <https://github.com/shangchang-app/onstage-source> | 完整源码、构建配置、`package-lock.json`、文档、CI |
| V1.6 预览 | <https://shangchang-app.github.io/onstage-source/> | 由 CI 从 `main` 的源码自动构建 |
| 线上仓库 | <https://github.com/shangchang-app/onstage> | 只放发布包 `site.zip` 和发布脚本 |
| 线上网站 | <https://shangchang-app.github.io/onstage/> | 目前仍是 V1.4.1，没有改动 |

预览和线上都在 `shangchang-app.github.io` 下，**属于同一个源（origin）**，浏览器本地存储是共用的。这带来两个结果：

- 好处：可以在同一个浏览器里真实模拟「旧版 → 新版」的升级。先在线上 V1.4.1 写草稿，再打开预览，V1.6 读到的就是旧版留下的数据（见第 4 节）。
- 注意：**打开过预览的浏览器，本地数据会被 V1.6 迁移一次**。迁移只复制、不删除，所以回到线上 V1.4.1 时，旧草稿还在（见第 5 节）。

## 2. 构建是可复现的

- 从干净检出开始构建，按 `README.md` 的「从干净检出生成待发布网站」操作。
- CI（`.github/workflows/preview.yml`）每次推送都会重新做一遍：`npm ci` → 类型检查 → 单元测试 → 构建线上发布包（前缀 `/onstage`）并做静态测试 → 打包 → 构建预览（前缀 `/onstage-source`）并做静态测试 → 发布 Release → 部署预览。
- `version.json` 写入四项：`version`、`commit`（源码提交号）、`builtAt`（构建时间）、`base`。
- 发布包和源码的对应关系：Release 标签 `build-<提交号>` 指向构建用的那次提交；发布包里的 `version.json` 写着同一个提交号；Release 说明里写着发布包的 SHA256。
- 同一次提交，在不同时间或不同机器上构建：网站功能完全一样，但 `builtAt` 和 Next.js 的构建编号不同，所以 **zip 的校验值会不同**。上线时请用 Release 里的那个文件，它的校验值已经记录在案。

## 3. 测试分两套，不能互相代替

| 测试 | 命令 | 测的是什么 |
|---|---|---|
| 单元测试 | `npm test` | 内容校验、规则检查、成果保存、导出导入、旧版草稿迁移、保存条件等（47 项） |
| **静态版测试** | `npm run test:pages` | 在模拟的 GitHub Pages 子路径下打开打包后的静态网站，用 Chromium 实测（21 项） |
| 正式版测试 | `npm run test:e2e` / `test:deploy` | 带服务器的版本，**和静态部署无关** |

线上和预览用的都是静态版，验收以静态版测试为准。

## 4. 同源升级测试（在真实网站上手工做一次）

1. 用一个**没有打开过预览**的浏览器（或清空 `shangchang-app.github.io` 的网站数据），打开线上 V1.4.1：`/onstage/experiences/ops-returns/work/`。在「跟着尝试」里随便写两格，等页面显示「已保存」。
2. 在同一个浏览器里打开预览：`/onstage-source/experiences/ops-returns-deep/work/`。应该看到第 1 步写的内容出现在完整版里。
3. 打开预览的短版 `/onstage-source/experiences/ops-returns/work/`，应该从第 1 步「收到任务」正常开始。
4. 回到线上 V1.4.1 的 `/onstage/experiences/ops-returns/work/`，原来写的内容应该还在（步骤回到第 1 步）。

自动测试里也有同样的场景：先写入一份 V1.4.1 格式的数据，再打开 V1.6。

## 5. 回滚与本地数据兼容性

**备份**：线上仓库的标签 `v1.4.1-live` 指向当前线上的部署提交 `5eed8ae`。该提交里的 `site.zip`，sha256 是 `10d61ad446206bcc95fcf76827a61d54b5bae5f06f2b6fd35c0c7b6e0cb44f23`。

**回滚步骤**（把线上恢复到 V1.4.1）：

1. 打开 `https://github.com/shangchang-app/onstage/tree/v1.4.1-live`，下载 `site.zip`，核对 sha256。
2. 在线上仓库 `main` 的根目录，删掉当前的 zip，上传这个 `site.zip`。根目录只能有一个 zip。
3. 等 Actions「Publish trial site」变绿。打开 `/onstage/` 确认首页是 V1.4.1，页脚没有版本号。

**本地数据在升级、回滚时会怎样**：

| 数据（浏览器 localStorage） | V1.4.1 → V1.6 | 回滚到 V1.4.1 |
|---|---|---|
| `onstage-free:v1` 草稿库 | V1.6 增加 `schema: 2`；6 步作答**复制**到 `ops-returns-deep`，原处保留，步骤号重置为第 1 步 | V1.4.1 忽略 `schema` 字段；原来的 6 步作答还能看到和继续编辑；它的「我的」会把 `ops-returns-deep` 显示成「已下线的体验」 |
| V1.6 短版的作答（`plan.*`） | 和旧作答一起存在 `ops-returns` 草稿里 | V1.4.1 不显示这些字段，也不会删除它们 |
| 成果 `onstage-works:v1` | V1.6 新增 | V1.4.1 不读，数据保留；再升级时又能看到 |
| 本机暂存、「感受」 | 复制一份到 `ops-returns-deep`，原处保留 | 不受影响 |
| 回滚后再升级 | 已经迁移过（`schema: 2`），不会再迁移一次 | — |

**已知限制**：
- 回滚后，在 V1.6 完整版里新写的内容（存在 `ops-returns-deep` 下），在 V1.4.1 里看不到；数据仍然保留，重新升级后可以看到。
- 回滚期间在 V1.4.1 里新写的 6 步作答，重新升级时不会再复制到完整版（迁移只做一次）。它们仍保留在 `ops-returns` 下，并会包含在导出的备份里。

## 6. 正式发布 V1.6（验收通过后）

1. 在源码仓库的 Releases 里找到 `build-<提交号>`，下载 `onstage-site-1.6.0-<提交号>.zip`，核对 `.sha256`。
2. 线上仓库：删除 `site.zip`，上传新的 zip（文件名不重要，但根目录只能有一个 zip）。
3. 等 Actions 变绿后打开 `/onstage/version.json`，`commit` 应该和 Release 的提交号一致。
4. 按第 4 节的方法，用一个老用户的浏览器检查一遍旧草稿。

## 7. 已知问题与未验证事项

- 真机没有验证：iPhone Safari、安卓浏览器、微信内置浏览器（重点：下载备份文件、选择导入文件、7 天清理）。
- 在中国大陆用手机流量访问 `github.io` 的速度和稳定性没有验证。
- 没有测试打印机或「存为 PDF」的实际输出，只验证了打印样式会隐藏导航。
- 浏览器「长期保留数据」请求在 Safari 和微信里是否生效，没有验证。
- 两个完整体验的内容都**未经从业者审核**。
- 学生实际完成用时没有测过（40–50 分钟是估算）。
- 成果只存在本机：没有跨设备同步，也没有公开分享链接。这是有意的限制，不是故障。
